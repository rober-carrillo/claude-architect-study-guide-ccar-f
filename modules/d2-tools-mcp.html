Task 2.4

Transports and lifecycle

stdio vs HTTP, and the handshake.

  • stdio: the host launches the server as a subprocess and talks over stdin/stdout. Used for local tools. Never print logs to stdout, because that corrupts the JSON-RPC stream. Log to stderr.
  • Streamable HTTP: a remote server at a URL, with auth headers or OAuth. Used for shared or hosted services. (The older HTTP+SSE transport is deprecated.)

The lifecycle, from config file to tool result

    "inputSchema": {
      "type": "object",
      "properties": {

        "status": { "type": "string", "enum": ["open", "closed", "any"], "default": "open" },
        "limit":  { "type": "integer", "minimum": 1, "maximum": 50, "default": 10 }
      },
      "required": ["query"]
    },
    "annotations": { "readOnlyHint": true }
  }
]}}
tools/call → request and resultone invocation
// request (host → server)
{ "jsonrpc": "2.0", "id": 7, "method": "tools/call",
  "params": { "name": "get_ticket", "arguments": { "ticket_id": "TCK-9999" } } }

// result (server → host): a tool-level error, reported as data
{ "jsonrpc": "2.0", "id": 7, "result": {
  "isError": true,
  "content": [{ "type": "text",
    "text": "{\"errorCategory\":\"not_found\",\"isRetryable\":false,\"message\":\"No ticket TCK-9999. Use search_tickets to find valid IDs.\"}" }]
}}

There are two kinds of failure. A protocol error (unknown method, malformed request) comes back as a JSON-RPC error and the model never sees it. A tool execution error (not found, permission denied, upstream timeout) comes back as a normal result with isError: true, so Claude can read it and change course.

Task 2.4

One tool call, end to end

A remote ticketing server traced from config to result, so you can see which layer adds what.

Scope

Auth protocols, OAuth and HTTP streaming are officially out of scope. This walkthrough is here so the layers make sense. The exam-relevant parts are .mcp.json with ${ENV} expansion, isError, and that Claude only ever sees the tool name, arguments and result.

1. Config: where the credential is referenced

.mcp.jsoncommitted, so no secrets inside
{
  "mcpServers": {
    "tickets": {
      "type": "http",
      "url": "https://mcp.acme-support.com/mcp",
      "headers": { "Authorization": "Bearer ${ACME_TICKETS_TOKEN}" }
    }
  }
}

2. What Claude produces: no credential, just intent

tool_use blockin the Messages API response
{ "type": "tool_use", "id": "toolu_01HtV9mXq3",
  "name": "mcp__tickets__search_tickets",
  "input": { "query": "double charge", "status": "open", "limit": 5 } }

3. What the host sends: JSON-RPC, credential in the transport

HTTP requesthost → MCP server
POST /mcp HTTP/1.1
Host: mcp.acme-support.com
Authorization: Bearer atk_live_7f3c9e...
Content-Type: application/json
Accept: application/json, text/event-stream
Mcp-Session-Id: 4b1e8f2a-91c3-4d7e-a0b5-3f6c2d9e8a71

{"jsonrpc":"2.0","id":7,"method":"tools/call",
 "params":{"name":"search_tickets","arguments":{"query":"double charge","status":"open","limit":5}}}

The host removes the mcp__tickets__ prefix, wraps the call in JSON-RPC, and adds the header it expanded from the environment. For a stdio server there are no headers: the credential is an environment variable given to the process at launch, and the same JSON-RPC objects travel over stdin and stdout, one per line.

4. The server checks the caller, then uses its own backend credential

Two separate secrets: the caller's token (who is calling this MCP server) and the server's backend token (how the server reaches Zendesk or the database). The second never leaves the server.

5. The result, and what Claude gets back

JSON-RPC resultserver → host
{"jsonrpc":"2.0","id":7,"result":{
  "content":[{"type":"text","text":"{\"tickets\":[{\"id\":88412,\"title\":\"Charged twice for March invoice\",\"status\":\"open\"}]}"}],
  "structuredContent":{"tickets":[{"id":88412,"title":"Charged twice for March invoice","status":"open"}]},
  "isError":false}}
tool_result blockhost → Claude, next user message
{ "type": "tool_result", "tool_use_id": "toolu_01HtV9mXq3",
  "content": [{ "type": "text", "text": "{\"tickets\":[{\"id\":88412, ...}]}" }] }

Task 2.2

Minimum servers

Python and TypeScript skeletons.

tools/tickets_server.pypip install mcp
import json, sys
from typing import Literal
try:
    from mcp.server.mcpserver import MCPServer as FastMCP   # mcp 2.x
except ImportError:
    from mcp.server.fastmcp import FastMCP                  # mcp 1.x

mcp = FastMCP("tickets")              # server name → tools become mcp__tickets__*

# TOOL: the function signature becomes inputSchema; the docstring becomes description
@mcp.tool()
def search_tickets(query: str,
                   status: Literal["open", "closed", "any"] = "open",
                   limit: int = 10) -> list[dict]:
    """Search support tickets by keyword. Use when you don't have a ticket ID.
    Returns id, title, status for each match. Call get_ticket for the full thread."""
    return db.search(query, status, min(limit, 50))

@mcp.tool()
def get_ticket(ticket_id: str) -> dict:
    """Get one ticket's full thread and metadata by ID (format TCK-1234)."""
    t = db.get(ticket_id)
    if t is None:
        # Raising inside a tool → returned to Claude as isError: true
        raise ValueError(f"No ticket {ticket_id}. Use search_tickets to find valid IDs.")
    return t

# RESOURCE: read-only context addressed by URI (static or templated)
@mcp.resource("tickets://categories")
def categories() -> str:
    """All ticket categories and their routing teams."""
    return json.dumps(db.categories())

@mcp.resource("tickets://{ticket_id}")
def ticket_resource(ticket_id: str) -> str:
    return db.render_markdown(ticket_id)

# PROMPT: a user-invoked template
@mcp.prompt()
def triage(ticket_id: str) -> str:
    return f"Triage ticket {ticket_id}: classify, set priority, draft a first reply."

if __name__ == "__main__":
    print("tickets server starting", file=sys.stderr)   # stderr, never stdout
    mcp.run()                                           # stdio by default
Version note

In the mcp Python package 2.x, mcp.server.fastmcp was replaced by mcp.server.mcpserver.MCPServer. The decorators work the same way. The snippet above imports whichever exists; it was run against mcp 1.30 and 2.3 in Lab 02. The exam tests the concepts (tools, resources, isError), not import paths.

Minimum server: TypeScript

src/server.tsnpm i @modelcontextprotocol/sdk zod
import { McpServer } from "@modelcontextprotocol/sdk/server/mcp.js";
import { StdioServerTransport } from "@modelcontextprotocol/sdk/server/stdio.js";
import { z } from "zod";

const server = new McpServer({ name: "tickets", version: "1.0.0" });

server.registerTool(
  "get_ticket",
  {
    title: "Get ticket",
    description: "Get one ticket's full thread and metadata by ID (format TCK-1234).",
    inputSchema: { ticket_id: z.string().regex(/^TCK-\d+$/).describe("Ticket ID") },
    annotations: { readOnlyHint: true },
  },
  async ({ ticket_id }) => {
    const t = await db.get(ticket_id);
    if (!t) {
      return { isError: true,
               content: [{ type: "text", text: `No ticket ${ticket_id}. Use search_tickets.` }] };
    }
    return { content: [{ type: "text", text: JSON.stringify(t) }] };
  }
);

await server.connect(new StdioServerTransport());
Task 2.2

What runs inside a tool

The model never sees or runs your tool's code. It sees the name, description and schema, and gets back the result.

The body of an MCP tool is ordinary deterministic code: a SQL query, an HTTP call, a file read. That makes the tool a control boundary. Claude can do exactly what the function allows and nothing else.

tickets_server.pya realistic body
@mcp.tool()
def search_tickets(query: str,
                   status: Literal["open", "closed", "any"] = "open",
                   limit: int = 10) -> dict:
    """Search support tickets by keyword. Use when you don't have a ticket ID.
    Returns id, title, status per match. Call get_ticket for the full thread."""
    sql = """SELECT id, title, status FROM tickets
             WHERE to_tsvector(title || ' ' || body) @@ plainto_tsquery(%s)
               AND (%s = 'any' OR status = %s)
             ORDER BY updated_at DESC LIMIT %s"""
    try:
        rows = db.execute(sql, (query, status, status, min(limit, 50)))
    except TimeoutError:
        raise ToolError(json.dumps({"errorCategory": "transient", "isRetryable": True,
                                    "message": "Ticket DB timed out. Retry in a few seconds."}))
    return {"tickets": [dict(id=r[0], title=r[1], status=r[2]) for r in rows],
            "count": len(rows)}          # count: 0 is a VALID empty result, not an error
  • Three columns, a 50-row cap, and no arbitrary SQL: narrow, purpose-built access.
  • A timeout is reported as an error with category and retryability. An empty match returns success with count: 0.
  • If the tickets were local Markdown files, you wouldn't need a server at all: the built-in Grep tool would do. MCP is for systems Claude can't reach directly.

Trap
  • Returning an empty result and success when the lookup actually failed (timeout, auth). The agent then reports "no records found" as fact. Distinguish "valid empty result" from "couldn't check".
  • Generic errors like "Operation failed". The agent can't tell a retryable timeout from a business-rule refusal, so it retries forever or gives up too early.
  • Fixing wrong tool selection by adding a routing classifier or few-shot examples before fixing the descriptions. Fix the descriptions first. It is the cheapest change and goes to the root cause.
Task 2.1

Tool descriptions and boundaries

Descriptions are the main input Claude uses to choose a tool. This is the most-tested idea in the domain.

Before and after

Minimal (misroutes)

get_customer:  "Retrieves customer information."
lookup_order:  "Retrieves order details."

"Check my order #12345" goes to get_customer about a third of the time.

Differentiated

lookup_order: "Get one order by order number
(format ORD-12345 or #12345). Returns status,
items, totals, shipping, refund_eligible.
Use for ANY question about a specific order.
Do NOT use to find who a customer is; use
get_customer (email/phone/customer ID)."

A good description includes input formats, example queries, edge cases, what it returns, and when to use it instead of similar tools.

The system prompt can override good descriptions

If the system prompt says "Always analyze the content the user provides", a tool called analyze_content picks up a keyword association and gets chosen for everything. When tool selection is wrong, check the system prompt for keyword-sensitive instructions, not just the descriptions.

Rename, split or merge

SymptomFixExample from the guide
Two tools with near-identical purpose and descriptionsRename and rewrite to remove the overlapanalyze_content → extract_web_results, with a web-specific description
One generic tool doing several jobs inconsistentlySplit into purpose-specific tools with clear input/output contractsanalyze_document → extract_data_points, summarize_content, verify_claim_against_source
Steps that always run togetherMerge. This is valid, but more work than fixing descriptions, so it's rarely the "first step"list_slots + create_event → schedule_meeting
A tool that is too open-endedConstrain itfetch_url → load_document, which validates the URL is an allowed document source
Exam signal

"Most effective first step to improve tool selection" → expand the descriptions. Few-shot routing examples add tokens without fixing the cause, a keyword router bypasses the model's understanding, and merging is a bigger architectural change.

Structured error responses

The error you return decides whether the agent retries, rephrases, explains or escalates.

errorCategoryExampleisRetryableAgent should
transientTimeout, 503, rate-limitedtrueRetry (ideally inside the tool or subagent first)
validationOrder ID in the wrong formattrue after fixing inputCorrect the arguments and call again

permissionAgent lacks scope to edit billingfalseEscalate; retrying is pointless
business-rule errorisError: true, content is structured
{ "isError": true, "content": [{ "type": "text", "text":
  "{\"errorCategory\":\"business\",\"isRetryable\":false,
    \"code\":\"RETURN_WINDOW_CLOSED\",
    \"message\":\"Order ORD-44170 was delivered 42 days ago; returns close after 30.\",
    \"customerMessage\":\"This order is outside our 30-day return window, but I can check warranty options.\"}" }] }

Empty result vs. failed lookup

Valid empty result

isError: false, {"matches": [], "count": 0}. The query ran and nothing matched. That is an answer.

Access failure

isError: true, transient. The query didn't run. Saying "no records found" would be a false statement.

Recover locally, propagate what you can't fix

A subagent should retry transient failures itself. Only when it can't recover does it report to the coordinator, with the failure type, what it tried, partial results and possible alternatives.

Task 2.3

Distributing tools and setting tool_choice

Which agent gets which tools, and how to force a call.

  • Fewer tools, better choices. An agent with 18 tools chooses worse than one with 4–5.
  • Tools outside a role get misused. A synthesis agent given web search starts searching instead of synthesizing.
  • Scoped cross-role tools for frequent needs: give the synthesis agent a narrow verify_fact for the 85% of checks that are simple, and keep complex verification going through the coordinator to the search agent.

Task 2.5

Built-in tools: Read, Write, Edit, Bash, Grep, Glob

Scenario 4's bread and butter. Know which tool answers which question.

ToolAnswersExample
Grep"Which files contain this text?"All callers of calculateTax(; where an error message is raised; every import … from "legacy/db"
Glob"Which files are named like this?"**/*.test.tsx; src/**/migrations/*.sql
Read"Show me this whole file."Follow an import to understand a flow
Edit"Replace this exact, unique text."Change one function's body
Write"Replace or create the whole file."New file; or the fallback when Edit can't find a unique anchor
Bash"Run a command."Tests, linters, git, build

Edit fails on non-unique text

Edit needs its old_string to appear exactly once. If the same line appears in three places, Edit fails. The reliable fallback is Read the whole file, then Write it back with the change.

Explore incrementally

  1. Grep for the entry point (the route, the CLI command, the error string).
  2. Read that file and follow its imports with more Reads.
  3. Only read what the trace needs. Reading every file first exhausts the context.

Tracing through wrapper modules

When utils/index.ts re-exports functions under new names, Grepping for the original name misses callers. First list every name the wrapper exports, then Grep for each of those names across the codebase.

Task 4.1

Write criteria, not adjectives

Vague

"Be conservative and only flag important issues." "Only report high-confidence findings."

Every reader interprets "important" differently, and the model's self-reported confidence isn't calibrated.

Explicit

"Flag: SQL built by string concatenation; secrets in source; missing auth check on a route. Do not flag: naming, formatting, or anything the linter catches."

Define each category, give a concrete example of each, and state what is out of scope.

Further habits that pay off: separate instructions, context and data with XML tags (<contract>…</contract>); explain why a rule exists so the model can apply it to new cases; put long documents first and the question last.

Task 4.1

Explicit criteria, severity rubrics and developer trust

False positives aren't just noise. They make developers ignore the accurate findings too.

Vague

"Check that comments are accurate."

Explicit

"Flag a comment only when the behaviour it claims contradicts what the code actually does. Skip TODOs, style, and comments that are merely incomplete."

A severity rubric with code examples

review-criteria.mdimported by CLAUDE.md for CI
## Report
- HIGH: exploitable or data-corrupting.
  e.g. `db.query("SELECT * FROM users WHERE id=" + req.params.id)`
- MEDIUM: wrong result in a realistic path.
  e.g. `if (total > limit)` where the spec says "at or above the limit"
- LOW: latent bug unlikely to trigger.
  e.g. unhandled promise in a shutdown hook

## Do not report
- Formatting, naming, import order (the linter owns these)
- Patterns used consistently across this repo (e.g. our `Result<T>` wrapper)

When one category is noisy

If "documentation accuracy" findings are wrong 60% of the time while "security" is 95% right, developers start dismissing both. Temporarily disable the noisy category to restore trust, and improve its prompt separately before turning it back on.

Trap

"Be conservative", "only report high-confidence findings" and "think carefully before flagging" don't improve precision. Only specific categorical criteria do.

Task 4.2

Few-shot examples: for ambiguity, not for volume

Use 2–4 examples that cover the hard or ambiguous cases, each showing the reasoning for the choice, rather than ten easy ones. Vary them so the model generalizes instead of copying surface features. Few-shot is the right fix when output is inconsistent on judgement calls or format drifts between runs.

few-shot blockinside the system prompt
<examples>
  <example>
    <input>Invoice lists "Net 30" and a due date of 2026-05-01 that disagree.</input>
    <output>{"due_date": "2026-05-01", "due_date_source": "explicit",
             "conflict": "Net 30 implies 2026-04-28"}</output>
    <why>An explicit date wins over computed terms; record the conflict, don't hide it.</why>
  </example>
  <example>
    <input>No due date anywhere on the invoice.</input>
    <output>{"due_date": null, "due_date_source": "absent", "conflict": null}</output>
    <why>Missing data is null. Never infer a date that isn't on the page.</why>
  </example>
</examples>
Task 4.2

Five jobs few-shot examples do well

Few-shot is the guide's answer when "detailed instructions alone produce inconsistent results".

JobExample set
Consistent output formatTwo findings in exactly location · issue · severity · suggested fix form
Ambiguous-case judgementAn example where the request could fit two tools, with the reasoning for picking one
Acceptable pattern vs real issueOne snippet that looks risky but is fine in this codebase; one that is a real bug
Varied document structuresCitations inline vs in a bibliography; methods in a section vs embedded in prose
Reducing hallucination and empty fieldsInformal measurements ("about two cups" → 0.47 L, flagged approximate); a field that is present but phrased unusually, so it isn't returned as null

Use 2–4 targeted examples that show why one choice beat the plausible alternative. That lets the model generalize to new cases rather than only match the examples. Five easy examples of the obvious case teach nothing.

Task 4.3

Getting JSON that is guaranteed to parse

MethodGuaranteeNotes
Structured outputs (JSON schema response format)Output matches the schema (constrained decoding)Strongest syntax guarantee. The request parameter name has changed across API versions, so check current docs.
Forced tool use: tool_choice: {"type":"tool","name":…}Claude must call that tool, so you read block.input as your JSONThe classic extraction pattern. With strict: true on the tool, the input also matches the schema.

Version note

Anthropic's current API docs say forced tool choice ({"type":"tool"}) and "any" are not accepted by the newest models (Sonnet 5.5, Opus 5.5, Fable 5.1) and return a 400. There you use auto plus strict: true and an explicit instruction, and treat a missing tool call as a retryable error. Lab 03 does both. This is not tested live here. For the exam, answer with the guide's concepts: forced selection makes a specific tool run, and any guarantees some tool call.

Exam signal

The official exam guide names tool use with a JSON schema as "the most reliable approach for guaranteed schema-compliant structured output". When an answer option says "define an extraction tool and read the tool_use input", that is the exam's preferred answer.

extract_invoice.pyforced tool use + validate + retry
INVOICE_TOOL = {
  "name": "record_invoice",
  "description": "Record fields extracted from one invoice.",
  "input_schema": {
    "type": "object",
    "properties": {
      "vendor":      {"type": "string"},
      "invoice_no":  {"type": ["string", "null"]},           # nullable: may be absent
      "currency":    {"type": "string", "enum": ["USD", "EUR", "CLP", "OTHER"]},
      "currency_other": {"type": ["string", "null"]},        # detail when OTHER
      "line_items":  {"type": "array", "items": {
          "type": "object",
          "properties": {"desc": {"type": "string"}, "amount_cents": {"type": "integer"}},
          "required": ["desc", "amount_cents"]}},
      "stated_total_cents":     {"type": "integer"},
      "calculated_total_cents": {"type": "integer"},          # lets you detect mismatches
    },
    "required": ["vendor", "invoice_no", "currency", "line_items",
                 "stated_total_cents", "calculated_total_cents"],
  },
}

def extract(doc: str, max_attempts: int = 3):
    messages = [{"role": "user", "content": f"<invoice>{doc}</invoice>\nExtract the fields."}]
    for _ in range(max_attempts):
        resp = client.messages.create(model="claude-sonnet-5-5", max_tokens=2048,
            tools=[INVOICE_TOOL], tool_choice={"type": "tool", "name": "record_invoice"},
            messages=messages)
        call = next(b for b in resp.content if b.type == "tool_use")
        problems = semantic_checks(call.input)   # e.g. line items don't sum to total
        if not problems:
            return call.input
        # Retry WITH the specific error, so the model can correct itself
        messages += [{"role": "assistant", "content": resp.content},
                     {"role": "user", "content": [{"type": "tool_result",
                       "tool_use_id": call.id, "is_error": True,
                       "content": f"Validation failed: {problems}. Re-read the document and fix."}]}]
    return route_to_human(doc, problems)
Exam signal
  • A schema fixes syntax, not truth. Constrained output can still put the tax in the subtotal field or invent a value. Catch semantic errors with code checks (sums, date order, cross-field rules) and a retry that includes the specific error.
  • Make fields nullable when the source may not contain them. A required non-null field pushes the model to fabricate.
  • Enum + "other" + a detail field keeps categories clean without forcing wrong buckets.
  • Retrying is pointless when the information isn't in the source. Detect "absent" and return null or escalate.
  • Extracting stated_total next to calculated_total is a self-check pattern: the mismatch flags records for review.
Task 4.3

Schema design patterns and tool_choice sequencing

How to shape a schema so it can say "I don't know" honestly.

contract extraction schemafragment
{
  "governing_law": { "type": ["string", "null"],
                     "description": "Null if the contract does not state it." },
  "termination_type": { "type": "string",
                        "enum": ["for_cause", "for_convenience", "mutual", "unclear", "other"] },
  "termination_other_detail": { "type": ["string", "null"] },
  "auto_renewal": { "type": ["boolean", "null"] },
  "effective_date": { "type": ["string", "null"],
                      "description": "ISO 8601 (YYYY-MM-DD). Convert '1st March 2026' → 2026-03-01." }
}
  • Nullable where the source may not contain the value. A required, non-null field invites fabrication.
  • "unclear" for genuinely ambiguous text; "other" + detail for categories you didn't anticipate.
  • Normalization rules in the prompt (and descriptions) alongside the strict schema handle messy source formats.

Task 4.4

Validation, retry and feedback loops

Knowing when a retry will work, and when it can't.

A retry message that works

Include three things: the original document, the failed extraction, and the specific validation errors.

retry promptspecific, not "try again"
<document>…original invoice text…</document>
<previous_extraction>{"subtotal_cents": 118000, "tax_cents": 0, "stated_total_cents": 129800, …}</previous_extraction>
<errors>
- line_items sum to 118000 but stated_total is 129800 (difference 11800 = 10% of subtotal)
- tax_cents is 0 but the document shows "IVA 10%"
</errors>
Re-read the document and correct only the fields involved in these errors.

Retry will likely fix

  • Format mismatch (date as "03/04/26")
  • Value placed in the wrong field
  • Structural output errors
  • Arithmetic that doesn't reconcile when the numbers are in the document

Retry can't fix

  • The value isn't in the document
  • It's only in an external document you didn't provide ("see Schedule B")
  • The source itself is contradictory, so flag conflict_detected instead

Learning from dismissals: detected_pattern

Add a detected_pattern field to every review finding (e.g. "string-concat-sql", "missing-null-check"). When developers dismiss findings, group the dismissals by pattern to see exactly which construct produces false positives, then fix that criterion.

The Message Batches API in depth

Submit many ordinary Messages requests at once, collect results later, and pay half.

batch = client.messages.batches.create(requests=[
    {"custom_id": f"invoice-{doc.id}",
     "params": {"model": MODEL, "max_tokens": 1024, "tools": [INVOICE_TOOL],
                "tool_choice": {"type": "tool", "name": "record_invoice"},
                "messages": [{"role": "user", "content": doc.text}]}}
    for doc in docs])

while client.messages.batches.retrieve(batch.id).processing_status != "ended":
    time.sleep(60)

failed = []
for r in client.messages.batches.results(batch.id):       # NOT in submission order
    if r.result.type == "succeeded":
        save(r.custom_id, r.result.message.content[0].input)
    else:
        failed.append(r.custom_id)                         # errored | expired | canceled
# Resubmit only `failed`, e.g. chunking documents that exceeded the context limit

SLA arithmetic

You promise results within 30 hours of a document arriving, and a batch can take 24. The worst case is a document arriving just after a submission: it waits for the next window, then takes 24 h. So window + 24 ≤ 30, meaning you submit at least every 6 hours, and every 4 to leave a margin. That is the guide's example.

Before a big batch

Refine the prompt on a sample set first. A prompt bug found after 50,000 documents means paying for 50,000 more.

WorkloadBatch?
Overnight technical-debt report, weekly audit, nightly test generationYes
Backfill extraction of 200k archived documentsYes
Blocking pre-merge checkNo: someone is waiting, and there is no SLA
Agent that needs to call tools and continueNo: no multi-turn tool calling inside a request
Task 4.6

Self-evaluation patterns

  • Separate critic instance (evaluator–optimizer): a second call with its own rubric and no access to the generator's reasoning.
  • Verify against reality: run the tests, re-query the record, check that cited quotes really appear in the source. Execution beats introspection.
  • Built-in cross-checks: the stated vs calculated totals pattern, or asking for citations that code can verify.
  • Stop hooks: refuse to let the agent finish until a check passes.
Task 4.6

Multi-instance and multi-pass review

Why a second, independent reviewer finds what the author can't.

  • Self-review is weak: in the same session, the model keeps the reasoning that produced the code and is unlikely to question it. This is true even with extended thinking.
  • Independent instance: a fresh Claude call with the diff and the criteria, but not the generator's reasoning, catches subtler issues.
  • Multi-pass: per-file passes for local issues plus a separate integration pass for cross-file data flow. This avoids attention dilution and contradictory findings.
  • Confidence alongside each finding can be used to route review attention, once calibrated (see Domain 5).
Trap

"Run three reviews and keep only findings that appear in two" sounds rigorous, but it suppresses real bugs that a single pass catches only some of the time. "Use a larger context window" doesn't fix attention quality. "Make developers split PRs" moves the burden without improving the system.

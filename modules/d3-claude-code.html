Diagnosing "Claude behaves differently for different people"

  1. Run /memory in both sessions to see which memory files each one loaded.
  2. If the instructions are in someone's ~/.claude/CLAUDE.md, move them to the project file, which is committed.
  3. If they're in a subdirectory CLAUDE.md, check whether the other person is working in that directory.

Task 3.1

Settings and permissions

Not an official task statement, but you'll need it to read config snippets in questions.

.claude/settings.jsonteam-shared
{
  "permissions": {
    "allow": ["Bash(pnpm test:*)", "Bash(pnpm lint:*)", "Read", "mcp__jira__get_issue"],
    "ask":   ["Bash(git push:*)"],
    "deny":  ["Read(./.env)", "Read(./secrets/**)", "Bash(curl:*)"]
  },
  "env": { "NODE_ENV": "development" }
}

Precedence, highest first: managed policy → command-line flags → .claude/settings.local.json → .claude/settings.json → ~/.claude/settings.json. A deny rule wins over an allow rule.

Task 3.2

Skills: packaged expertise, loaded on demand

A skill is a folder with a SKILL.md plus any scripts, templates or reference docs it needs. Only the name and description sit in context all the time. The body loads when Claude decides the skill is relevant, and the bundled files load only if the body points to them. This is called progressive disclosure, and it is why you can install many skills without filling the context window.

.claude/skills/db-migration/SKILL.mdminimum skeleton
---
name: db-migration
description: Create and verify a Postgres schema migration. Use when the user asks to add,
  change or drop a table, column or index.
allowed-tools: Read, Write, Bash(pnpm migrate:*)
---
# Writing a migration

1. Generate the file: `pnpm migrate:new <name>`
2. Write both `up` and `down`. Follow the template in [template.sql](template.sql).
3. Run `scripts/check_locks.py <file>` and fix any table-lock warning
   before continuing. See [reference/locking.md](reference/locking.md).
4. Run `pnpm migrate:up` then `pnpm migrate:down` to prove it reverses.
.claude/skills/db-migration/ SKILL.md # required: frontmatter + instructions template.sql # loaded only if referenced and needed reference/locking.md scripts/check_locks.py # executed, not read into context

The description decides whether the skill ever fires, so write it as "what it does + when to use it", in the words a user would actually say. Newer builds also accept frontmatter such as context: fork (run the skill in an isolated subagent) and disable-model-invocation (only the user can trigger it).

Scope and personal variants

  • .claude/skills/ and .claude/commands/ in the repo: shared with the team via version control.
  • ~/.claude/skills/ and ~/.claude/commands/: personal.
  • Want your own version of a team skill? Create a personal one with a different name (e.g. review-strict) so you don't affect teammates.

Skill or CLAUDE.md?

CLAUDE.md is always loaded, for universal standards. Skills are loaded on demand, for task-specific workflows. Putting a 200-line release procedure in CLAUDE.md taxes every unrelated session.

Task 3.4

Plan mode

Plan mode (Shift+Tab to cycle modes, or --permission-mode plan) lets Claude read and explore but not edit or run anything that changes state. It finishes with a written plan for you to approve before any code changes.

Use plan mode

  • Changes touching many files or services
  • Unfamiliar codebase, or several valid approaches
  • Architectural decisions such as migrations, framework swaps or new module boundaries
  • When you want a reviewable plan before any edits happen

Skip it

  • Small, well-understood fixes (a typo, a one-function bug with a clear stack trace)
  • Changes where the diff is the plan
Trap

Plan mode is a workflow choice, not a safety control. To guarantee Claude can never touch production, use deny rules or hooks. Telling it to "stay in plan mode" is not enforcement.

Task 3.4

Plan mode, direct execution and the Explore subagent

The decision is about how much is unknown, not about how many lines change.

TaskModeWhy
Add a date-validation conditional to one functionDirectClear scope, one obvious approach
Fix a bug with a clear stack trace in one fileDirectThe trace tells you where and what
Migrate a logging library used in 45+ filesPlanMany files, ordering and compatibility decisions
Split a monolith into servicesPlanArchitectural decisions: service boundaries, dependencies
Choose between two integration approaches with different infrastructure needsPlanSeveral valid approaches; compare before committing

Combine them: plan the library migration in plan mode, approve the plan, then execute it directly. That's a common correct answer.

The Explore subagent

Discovery is verbose: dozens of Greps and Reads. Run it in the Explore subagent so that output stays in the subagent's context and only a summary returns. This prevents the main conversation from filling up during multi-phase tasks.

Trap

"Start in direct execution and switch to plan mode if it gets complicated" is wrong when the complexity is already stated in the task. "Let the implementation reveal the boundaries" means expensive rework later.

Task 3.6

Headless mode: claude -p

-p (print) runs a single prompt non-interactively and exits. Without it, Claude Code waits for input and the CI job hangs.

ci/review.shheadless review step
git diff origin/main...HEAD > /tmp/pr.diff

claude -p "Review the diff in /tmp/pr.diff against CLAUDE.md. Report only bugs and
security issues. Each finding: file, line, severity (high|medium|low), message, fix." \
  --output-format json \
  --max-turns 8 \
  --allowedTools "Read,Grep,Glob" \
  > review.json

# review.json → script that posts inline PR comments
FlagPurpose
-p "…"Non-interactive, single run
--output-format json / stream-jsonMachine-readable result, plus cost, session id and turn count
--json-schemaIn recent versions, validates the final answer against a schema for structured findings
--allowedTools / --disallowedToolsLeast privilege for the runner
--max-turnsBounds the run time and cost
--append-system-promptAdds CI-specific instructions on top of the defaults
--resume <id> / --continueContinue an earlier session
Task 3.6

GitHub Actions

.github/workflows/claude-review.ymlset up via /install-github-app
name: Claude PR review
on:
  pull_request:
    types: [opened, synchronize]

jobs:
  review:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: write
    steps:
      - uses: actions/checkout@v4
        with: { fetch-depth: 0 }
      - uses: anthropics/claude-code-action@v1
        with:
          anthropic_api_key: ${{ secrets.ANTHROPIC_API_KEY }}
          prompt: |
            Review this PR using the standards in CLAUDE.md.
            Comment only on bugs and security issues, inline at the exact line.
            Earlier review comments are below; do not repeat ones still unresolved.
          claude_args: "--max-turns 10 --allowedTools Read,Grep,Glob"

The action reads the repo's CLAUDE.md, so review standards live in one versioned place shared by local sessions and CI.

Task 3.6

Review and test-generation patterns

  • Independent reviewer. The session that wrote the code is a poor judge of it, because it carries its own reasoning forward. Review in a fresh session or a separate instance with no access to the author's chain of thought.
  • Split large reviews. One pass per file for local bugs, then one cross-file pass for integration issues (changed signatures, data flow). A single pass over 30 files gives shallow, inconsistent attention.
  • No duplicate comments on re-runs. Pass prior findings into the prompt and ask for new or still-unresolved issues only.
  • Reduce false positives at the criteria level. Explicit in-scope and out-of-scope lists, and a severity rubric with examples. If one category is noisy, disable that category until it is fixed, so developers don't learn to ignore every comment.
  • Test generation. Put the existing tests and fixtures in context (or point at them in CLAUDE.md) so new tests follow conventions and don't duplicate coverage. Run the tests in the loop: generate, run, read failures, fix.
  • Batch vs sync. Blocking pre-merge checks run synchronously. Nightly audits of the whole repo can use the Batch API at lower cost.
Trap

Asking the model to "self-review its own changes before finishing" in the same context is weaker than an independent review pass. Asking it to report only "high-confidence" findings doesn't fix false positives either, because self-reported confidence isn't calibrated. Tighten the criteria instead.

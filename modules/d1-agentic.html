Task 1.1

The agentic loop is driven by stop_reason

Continue on tool_use, stop on end_turn. Nothing else decides termination.

Every agent, whether hand-rolled on the Messages API or built with the Agent SDK, runs the same loop. Claude answers; if it asked for a tool, your code runs the tool and sends the result back; repeat until Claude stops asking.

flowchart LR
  A[messages + tools] --> B[Claude]
  B -->|"stop_reason = tool_use"| C["Run tool(s) in your code"]
  C -->|"tool_result blocks matched by tool_use_id"| A
  B -->|"stop_reason = end_turn"| D["Final answer"]
  B -->|"max_tokens, pause_turn, refusal"| E["Handle explicitly"]
agent_loop.pyraw Messages API
import anthropic

client = anthropic.Anthropic()
messages = [{"role": "user", "content": "Is order 4417 eligible for a refund?"}]

while True:
    resp = client.messages.create(
        model="claude-sonnet-5-5",
        max_tokens=4096,
        system="You are Acme's support agent. Verify the customer before any account action.",
        tools=TOOLS,          # list of {name, description, input_schema}
        messages=messages,
    )
    # Always append the full assistant turn, including tool_use blocks
    messages.append({"role": "assistant", "content": resp.content})

    if resp.stop_reason != "tool_use":   # "end_turn" = done
        break

    results = []
    for block in resp.content:
        if block.type == "tool_use":
            try:
                out = run_tool(block.name, block.input)
                results.append({"type": "tool_result", "tool_use_id": block.id, "content": out})
            except ToolError as e:
                # Errors go BACK to Claude so it can recover; don't crash the loop
                results.append({"type": "tool_result", "tool_use_id": block.id,
                                "content": str(e), "is_error": True})
    # All results for one turn go in ONE user message
    messages.append({"role": "user", "content": results})
Exam signal
  • Loop termination is decided by stop_reason, not by scanning the text for "done" or "final answer", and not by an arbitrary iteration cap used as the main control.
  • Tool results go in a user message as tool_result blocks, each tied to its tool_use_id. When Claude requests several tools in one turn, return all their results together in the next message.
  • A tool failure becomes is_error: true in the result so the model can adapt. It should not be an exception that kills the loop.
Task 1.3

Agent SDK: the same loop, packaged

query(), options, in-process tools.

The Claude Agent SDK (claude-agent-sdk for Python, @anthropic-ai/claude-agent-sdk for TypeScript) is the harness Claude Code runs on. It runs the loop for you and adds built-in tools (Read, Write, Edit, Bash, Grep, Glob, WebFetch…), permissions, sessions, subagents, hooks and MCP.

support_agent.pyminimum SDK skeleton
import asyncio, json
from claude_agent_sdk import (query, ClaudeAgentOptions, ResultMessage,
                              tool, create_sdk_mcp_server)

# 1. A custom tool, served by an in-process MCP server
@tool("lookup_order",
      "Look up one order by its ID (format ORD-12345). Returns status, total, "
      "purchase date and refund_eligible. Use before any refund decision.",
      {"order_id": str})
async def lookup_order(args):
    order = await db.get_order(args["order_id"])
    if order is None:
        return {"content": [{"type": "text",
                 "text": "No order with that ID. Ask the customer to confirm it."}],
                "is_error": True}
    return {"content": [{"type": "text", "text": json.dumps(order)}]}

billing = create_sdk_mcp_server(name="billing", version="1.0.0", tools=[lookup_order])

# 2. Options: who the agent is, what it may touch
options = ClaudeAgentOptions(
    system_prompt="You are Acme's support agent...",
    mcp_servers={"billing": billing},
    allowed_tools=["mcp__billing__lookup_order"],   # mcp__<server>__<tool>
    permission_mode="default",       # default | acceptEdits | plan | bypassPermissions
    max_turns=15,
)

# 3. Run: query() streams messages until the loop ends
async def main():
    async for msg in query(prompt="Can I get a refund on ORD-44170?", options=options):
        if isinstance(msg, ResultMessage):
            print(msg.result, msg.total_cost_usd, msg.session_id)

asyncio.run(main())

Task 1.3

Subagents: context isolation is the point

Explicit context, parallel Task calls, scoped tools.

A subagent is a separate Claude instance with its own system prompt, its own tool set and its own, empty context window. The coordinator invokes it through the Task tool (called Agent in newer Claude Code builds). The subagent works, and only its final message comes back to the coordinator.

flowchart TB
  U[User request] --> C[Coordinator agent]
  C -->|"Task: full brief + data"| S1["Subagent: web search"]
  C -->|"Task: full brief + data"| S2["Subagent: doc analysis"]
  C -->|"Task: full brief + data"| S3["Subagent: synthesis"]
  S1 -->|"final message only"| C
  S2 -->|"final message only"| C
  S3 -->|"final message only"| C
  C --> R[Answer]
research_coordinator.pysubagents in the SDK
from claude_agent_sdk import ClaudeAgentOptions, AgentDefinition

options = ClaudeAgentOptions(
    allowed_tools=["Task", "Read", "Grep", "Glob", "WebSearch"],  # coordinator needs Task
    agents={
        "web-researcher": AgentDefinition(
            # description = WHEN to delegate. The coordinator routes on this text.
            description="Finds and summarizes primary sources on the web. "
                        "Use for any factual claim that needs a citation.",
            prompt="You research one question. Return findings as a list of "
                   "{claim, source_url, quote, date}. Say what you could not find.",
            tools=["WebSearch", "WebFetch"],       # least privilege
            model="sonnet",
        ),
        "doc-analyst": AgentDefinition(
            description="Reads local documents and extracts facts with page refs.",
            prompt="...",
            tools=["Read", "Grep", "Glob"],
        ),
    },
)

Exam signal
  • Subagents inherit nothing. They do not see the coordinator's conversation. The Task prompt must carry everything: the goal, constraints, the data or prior findings, and the output format wanted.
  • Parallelism comes from emitting several Task calls in one assistant turn. Calls spread across turns run one after another.
  • The coordinator owns decomposition, routing, aggregation and error handling. Subagents should return structured results with metadata (source, date, confidence, gaps) so the coordinator can merge and cite them.
  • Give each subagent only the tools its role needs. A synthesis agent with web search will wander off and research instead of synthesizing.
  • Subagents are good for keeping noisy exploration (big file reads, many search results) out of the main context. Only the summary comes back.
Trap
  • "The final report missed whole subtopics" → the usual root cause is the coordinator's decomposition being too narrow, not the subagents doing poor work. Fix where the scope was set.
  • Answers that let subagents talk to each other directly, or share one global memory, break the hub-and-spoke model the exam favours. Route through the coordinator for observability and consistent error handling.
  • Not every task needs multiple agents. Fixed, predictable steps are better as a prompt chain (step 1 output → step 2 input) or a single agent. Multi-agent costs more tokens and adds coordination failure modes.

Orchestration patterns to recognise

PatternShapeUse when
Prompt chainingFixed sequence, each step's output feeds the next, with gates betweenSteps are known ahead of time (extract → validate → summarize)
RoutingClassifier picks one specialist pathDistinct input categories (billing vs tech support)

Task 1.2

Designing the coordinator

In a hub-and-spoke system the coordinator does most of the architecting. Most Scenario 3 questions are about what it does well or badly.

The coordinator's four jobs

JobDone wellDone badly (what the question will show)
DecomposeBreaks the topic into subtopics that together cover it, each distinct"AI in creative industries" split into three visual-arts subtopics, so music and film never get researched
SelectPicks only the subagents this query needsEvery query, even "what year was X founded", runs through search → analysis → synthesis → report
RouteAll subagent traffic passes through it, giving one place for logging, errors and controlSubagents call each other directly; a failure in one is invisible to the rest
Aggregate and checkReads synthesis output for gaps and sends targeted follow-upsAccepts the first synthesis even when whole sections say "no data"

Partition scope to avoid duplicated work

If two search subagents get overlapping briefs, they return the same five articles and you pay twice. Give each a distinct subtopic or source type:

Overlapping

Agent A: "Research AI in music."
Agent B: "Research AI and musicians' jobs."

Partitioned

Agent A: "Peer-reviewed studies on AI in music, 2022+."
Agent B: "Industry reports and labour statistics on music employment."

Brief subagents with goals and quality bars, not procedures

The official guide says coordinator prompts should "specify research goals and quality criteria rather than step-by-step procedural instructions". A subagent that only has steps can't adapt when step 2 finds nothing.

Procedural

"Search Google for 'AI music'. Open the first 5 results. Summarize each in 3 sentences."

Goal + criteria

"Find evidence on how generative AI changed music-production employment since 2022. Prefer primary data. Return 5–10 claims, each with source URL, date and a supporting quote. List the questions you couldn't answer."

The iterative refinement loop

flowchart LR
  C[Coordinator] -->|"targeted queries"| S[Search + analysis subagents]
  S -->|"structured findings"| Y[Synthesis subagent]
  Y -->|"draft + coverage gaps"| C
  C -->|"gaps remain"| S
  C -->|"coverage sufficient"| R[Report]

The coordinator reads the synthesis for gaps ("no data on film"), sends search and analysis subagents targeted follow-up queries, and runs synthesis again until coverage is good enough.

Multi-concern requests (Scenario 1 version)

"My order arrived damaged, I was charged twice, and I want to change my address." Split it into three distinct items, investigate each (in parallel where they're independent) using shared context such as the verified customer ID, then write one unified reply. Don't answer the first concern and drop the rest, and don't make three separate replies.

Trap

When a scenario says each subagent "completed successfully" but the output is incomplete, the fault is upstream in the coordinator's decomposition or selection. Answers that tune the search queries or the synthesis prompt fix the wrong layer.

Task 1.6

Choosing a decomposition strategy

Fixed pipeline or adaptive plan? It depends on whether you know the steps before you start.

Prompt chaining (fixed)

The steps are known in advance and always the same. Each step is a focused prompt whose output feeds the next.

  • Per-file review → cross-file integration review
  • Extract → validate → normalize → summarize
  • Multi-aspect review: security pass, then performance pass, then docs pass

Dynamic decomposition (adaptive)

The next subtasks depend on what the last step found. The plan changes as you learn.

  • "Add comprehensive tests to a legacy codebase"
  • Open-ended research questions
  • Debugging an intermittent production failure

Worked example: tests for a legacy codebase

  1. Map the structure first: entry points, modules, existing tests (Glob **/*test*, Grep for imports).
  2. Find high-impact areas: code that handles money, auth or most traffic, and has no tests.
  3. Write a prioritized plan, then start on the top item.
  4. Adapt: when you discover that billing/ depends on an untested tax/ module, add tax/ to the plan ahead of it.

Wrong answers here: "generate tests for every file alphabetically" (no prioritisation), "read every file first" (exhausts the context window), or a fixed plan written before looking at the code.

Worked example: splitting a large review

One pass over 14 files gives uneven depth and contradictory findings, because attention is diluted. Split it into a prompt chain:

review_chain.pyper-file passes, then integration
local_findings = []
for path in changed_files:                       # pass 1..N: one file each, focused attention
    local_findings += review_file(path, diff_for(path), criteria=CRITERIA)

integration = review_integration(                # final pass: cross-file data flow only
    summaries=[summarize(p) for p in changed_files],
    focus="changed signatures, shared state, call sites across files",
)
post_comments(dedupe(local_findings + integration))
Exam signal

"Predictable, multi-aspect review" → prompt chaining. "Open-ended investigation" → dynamic decomposition. If the question describes inconsistent depth across many files, the answer is to split the passes, not to use a bigger context window or require smaller PRs.

Task 1.5

Hooks: deterministic control over a probabilistic model

Deterministic guarantees vs probabilistic compliance.

A hook is your code, run by the harness at a lifecycle event. It executes whatever the model decides, which makes it the place for rules that must hold: compliance limits, blocking dangerous commands, normalizing data, audit logging.

EventFiresTypical use
PreToolUseBefore a tool runs; can allow, deny, ask, or modify the inputBlock refunds over a limit; block rm -rf; require approval
PostToolUseAfter a tool returnsRun the formatter or linter after edits; normalize or trim tool output before the model sees it
UserPromptSubmitWhen a prompt is submittedInject context, reject prompts that break policy
Stop / SubagentStopWhen the agent or a subagent finishesVerify the work is really done (tests pass) and send it back if not
PreCompactBefore context compactionSave the transcript or key facts first
SessionStart / SessionEndSession boundariesLoad environment context; clean up
NotificationWhen the agent needs attentionDesktop or Slack alert
refund_guard.pySDK hook, enforces a business rule
from claude_agent_sdk import ClaudeAgentOptions, HookMatcher

async def cap_refunds(input_data, tool_use_id, context):
    amount = input_data["tool_input"].get("amount", 0)
    if amount > 500:
        return {"hookSpecificOutput": {
            "hookEventName": "PreToolUse",
            "permissionDecision": "deny",           # allow | deny | ask
            "permissionDecisionReason":
                "Refunds over $500 need a human. Escalate with a case summary instead.",
        }}
    return {}   # no opinion → normal permission flow continues

options = ClaudeAgentOptions(hooks={
    "PreToolUse": [HookMatcher(matcher="mcp__billing__issue_refund", hooks=[cap_refunds])],
})
.claude/settings.jsonthe same idea as a Claude Code shell hook
{
  "hooks": {
    "PreToolUse": [
      { "matcher": "Bash",
        "hooks": [{ "type": "command", "command": ".claude/hooks/block-prod-db.sh" }] }
    ],
    "PostToolUse": [
      { "matcher": "Edit|Write",
        "hooks": [{ "type": "command", "command": ".claude/hooks/format.sh" }] }
    ]
  }
}

A command hook gets the event as JSON on stdin (tool_name, tool_input, session_id…). Exit code 0 means continue. Exit code 2 means block, and whatever the script wrote to stderr is fed back to Claude as the reason. A hook can also print a JSON decision to stdout instead.

Exam signal: prompt vs hook

"The agent occasionally skips identity verification before a refund" or "sometimes exceeds the refund limit". When a rule has financial, legal or safety consequences, the right answer is programmatic enforcement: a PreToolUse hook, or a tool that checks a prerequisite before running. A stronger prompt, few-shot examples or ALL-CAPS warnings only make compliance more likely. A hook makes it certain.

Tasks 1.4 · 1.5

Prerequisite gates, normalization and handoffs

Three hook and workflow patterns the guide names explicitly, with code you can adapt.

1. A prerequisite gate

"Block process_refund until get_customer has returned a verified customer ID." A prompt makes this likely, and a gate makes it certain. A gate is state your code keeps, checked before the tool runs.

gates.pyPreToolUse gate keyed on session state
verified = {}   # session_id -> customer_id, filled when get_customer succeeds

async def remember_verification(input_data, tool_use_id, context):      # PostToolUse
    if input_data["tool_name"] == "mcp__crm__get_customer":
        result = parse(input_data["tool_response"])
        if result.get("verified"):
            verified[input_data["session_id"]] = result["customer_id"]
    return {}

async def require_verification(input_data, tool_use_id, context):       # PreToolUse
    if input_data["tool_name"] in ("mcp__billing__lookup_order", "mcp__billing__process_refund"):
        if input_data["session_id"] not in verified:
            return {"hookSpecificOutput": {
                "hookEventName": "PreToolUse",
                "permissionDecision": "deny",
                "permissionDecisionReason": "Verify the customer with get_customer first.",
            }}
    return {}

The deny reason is sent back to Claude, so the agent learns what to do instead. A good gate redirects as well as blocks.

2. Normalizing tool output before Claude sees it

Three MCP servers return dates as 1767225600, "2026-01-01T00:00:00Z" and "01/01/26", and status as 3 or "SHIPPED". The agent then compares them wrongly. A PostToolUse hook can rewrite every result into one format so the model never has to guess.

normalize.pyPostToolUse: one format for every tool
STATUS = {1: "pending", 2: "paid", 3: "shipped", 4: "returned"}

def to_iso(v):
    if isinstance(v, (int, float)):                      # Unix seconds
        return datetime.fromtimestamp(v, tz=timezone.utc).isoformat()
    return dateparser.parse(v).astimezone(timezone.utc).isoformat()

async def normalize(input_data, tool_use_id, context):
    data = parse(input_data["tool_response"])
    for k in ("created_at", "shipped_at", "updated"):
        if k in data: data[k] = to_iso(data[k])
    if isinstance(data.get("status"), int):
        data["status"] = STATUS[data["status"]]
    keep = {"order_id", "status", "created_at", "shipped_at", "total_cents", "refund_eligible"}
    data = {k: v for k, v in data.items() if k in keep}  # trim the 40-field payload too
    return {"hookSpecificOutput": {"hookEventName": "PostToolUse",
            "additionalContext": json.dumps(data)}}

The exact mechanism for replacing or annotating a tool result differs between SDK versions. For the exam, what matters is that a PostToolUse hook can transform results before the model reasons over them.

Task 1.7

Sessions: resume, fork or start fresh

Long investigations span days. The choice is about whether the old context is still true.

SituationChooseHow
Picking up yesterday's investigation; little has changedResume the named sessionclaude --resume auth-refactor (SDK: resume=<session id>)
Resuming, but you've since edited 3 of the files it analyzedResume and say what changed"Since last time I changed auth/session.ts and auth/token.ts; re-check those two."
A large refactor landed; most earlier tool results are staleFresh session + injected summaryStart new and paste a structured summary of the conclusions that still hold
Want to compare two approaches from the same analysisForkfork_session=True with resume (CLI: --resume … --fork-session)
Context window full of exploration output, same task continues/compactSummarizes history in place; optionally say what to keep
fork_compare.pytwo strategies, one baseline
base = await run(query(prompt="Analyze the payments module's test gaps.", options=opts))
baseline_id = base.session_id

unit = query(prompt="Plan a unit-test-first strategy.",
             options=replace(opts, resume=baseline_id, fork_session=True))
contract = query(prompt="Plan a contract-test-first strategy.",
                 options=replace(opts, resume=baseline_id, fork_session=True))
# Each fork starts from the same analysis and diverges independently.
Trap
  • Resuming a session full of stale tool results means the agent "remembers" code that no longer exists. If the question stresses that the code changed a lot, start fresh with a summary.
  • Forking is for exploring alternatives. It is not a fix for a full context window. /compact is.
  • Re-exploring the whole codebase after a small change wastes the session. Tell it which files changed.

Crash recovery with manifests

For long multi-agent runs: each agent periodically writes its state (task, progress, findings so far) to a known location. A manifest lists those files. On restart the coordinator loads the manifest and injects each agent's saved state into its prompt, so work resumes instead of restarting.

state/manifest.jsonloaded by the coordinator on resume

  "run_id": "research-2026-10-10",
  "agents": {
    "web-search":   { "state": "state/web-search.json",  "status": "done" },
    "doc-analysis": { "state": "state/doc-analysis.json", "status": "in_progress", "cursor": 14 },
    "synthesis":    { "state": null, "status": "pending" }
  }
}

Task 5.1

What goes wrong as context grows

Failure modes and the techniques that fix them.

  • Lost in the middle: material in the middle of a very long context gets less attention than the beginning and end. Put key facts and instructions where they are easy to find, and repeat critical constraints near the end.
  • Summary drift: each round of summarizing turns specifics ("$1,240.50 charged twice on 3 March, order ORD-44170") into vague prose ("a billing issue"). Numbers, IDs and dates go first.
  • Tool-output bloat: a single API response with 40 fields per row fills the window with noise.
  • Stale context: after a long session, early tool results may no longer be true (files changed, tickets moved).

Task 5.1

Case facts, trimming and position-aware input

What a long support conversation actually sends to Claude on turn 30.

request on turn 30facts outside the summarized history
<system>You are Acme's support agent… (policies)</system>

<case_facts>            ← persistent, updated by code, never summarized
  customer_id: C-2201 (verified 14:02)
  issue_1: ORD-44170 duplicate charge, $1,240.50 × 2 on 2026-03-03, status: refund pending approval
  issue_2: ORD-44188 damaged item, photo received, replacement shipped TRK-889
  customer_expectation: "refund before Friday 2026-03-13"
</case_facts>

<summary_of_turns_1_24>…</summary_of_turns_1_24>
…turns 25–29 verbatim, with order lookups trimmed to 6 relevant fields…
<user>So when will I see the money?</user>
  • Summaries turn "$1,240.50 by Friday" into "a refund soon". The facts block keeps the exact values.
  • With several issues in one session, keep a structured entry per issue (ID, amount, status).
  • Trim tool results to the fields that matter before they pile up (6 of 40).
  • The Messages API is stateless: send the complete (managed) history on every request.

Mitigating lost-in-the-middle in aggregated input

When the synthesis agent receives 30 subagent reports, findings in the middle get dropped. Put a key-findings summary at the start, and organize the details under explicit section headers. If the downstream agent has a small context budget, change the upstream agents to return structured facts, citations and relevance scores instead of verbose reasoning.

Task 5.1

Handoffs between agents

A handoff is a context boundary. Whatever isn't written into the handoff is gone. A good handoff payload looks like this:

handoff payloadcoordinator → subagent, or agent → human
{
  "goal": "Decide whether ORD-44170 qualifies for a refund under policy v3",
  "facts": { "customer_id": "C-2201", "verified": true, "order_total_cents": 124050,
             "charged_twice": true, "charge_dates": ["2026-03-03", "2026-03-03"] },
  "done_so_far": ["Verified identity via DOB + last4", "Confirmed duplicate charge in Stripe"],
  "open_questions": ["Was the second charge already reversed by the bank?"],
  "constraints": ["Refunds over $500 require human approval"],
  "return_format": "{decision, reason, evidence[], needs_human: bool}"
}
Exam signal
  • Escalating to a human? Send a structured summary (customer, issue, what was tried, what's needed). The human shouldn't need to read the transcript.
  • Synthesizing many sources? Have subagents return claims with source, date and quote attached, so attribution survives the merge. When sources conflict, keep both with their sources rather than silently picking one.
  • "Agent forgets the order number after a long chat" → a persistent facts block, not a bigger context window.
Trap

"Use a model with a bigger context window" is rarely the best answer. A bigger window still has the lost-in-the-middle problem and costs more on every turn. Curating what goes in is usually the fix.

Task 5.2

When to escalate to a human

Good triggers

  • The customer explicitly asks for a human. Honour it right away rather than trying once more.
  • Policy is silent or ambiguous on this case (a policy gap)
  • The action is above an authority threshold (amount, account closure, legal)
  • The agent can't make progress: the same tool keeps failing, or information is missing and can't be obtained
  • Several plausible matches for an identity, so it can't be resolved safely

Weak triggers

  • Sentiment analysis alone ("customer sounds upset"). Frustration doesn't mean the case is complex.
  • The model's self-reported confidence score. It isn't calibrated.
  • Escalating everything. That defeats the point of the agent.
  • Escalating only after N turns. That number is arbitrary.
Exam signal

For an ambiguous identity (two customers named J. Smith), ask for one more identifier. Picking the most likely match is wrong. For a simple, in-policy request from a frustrated customer, resolve it while acknowledging the frustration. Escalate only if they ask for a person.

Task 5.2

Escalation: the fine print

Four situations that look alike and need different responses.

Customer says / tool returnsRight moveWhy
"I want to talk to a human."Escalate now, without investigating firstExplicit request; honour it
"This is ridiculous, my package is broken!" (simple, in-policy replacement)Acknowledge the frustration and offer the fix. Escalate only if they ask again for a humanFrustration is not complexity
"Match the competitor's price." Policy only covers price drops on your own siteEscalateThe policy is silent on this case (a policy gap)
get_customer returns 3 matches for "Maria Lopez"Ask for another identifier (email, order number)Never pick by heuristic

Calibrating escalation with the prompt

If the agent escalates easy cases and tries to handle hard ones, the first fix is explicit escalation criteria with few-shot examples in the system prompt: one "resolve" example (damaged item with photo → replace), one "escalate" example (policy exception). Classifiers, sentiment scores and self-rated confidence are the wrong answers.

Task 5.3

Error handling across agents

CategoryExampleRight response
TransientTimeout, 429, 503Retry with backoff, inside the tool or subagent
ValidationBad ID format, missing fieldReturn to the model with what's wrong, so it fixes the input
Business ruleRefund outside the windowNot retryable. Explain to the user, offer alternatives, or escalate.
Permission403, missing scopeNot retryable by the agent. Escalate or report.

In a multi-agent system, a subagent that fails should return structured failure context to the coordinator: what failed, the category, what it tried, any partial results, and possible alternatives. The coordinator then decides whether to retry, route around the gap, or continue with partial results.

Don't

  • Swallow the error and return an empty success. The gap disappears from the final answer.
  • Abort the whole workflow because one of five sources timed out
  • Return only "search failed"

Do

  • Continue with what succeeded and annotate coverage: "Section 3 lacks data from source X (timeout)"
  • Retry transient failures locally before escalating them
  • Keep "no results" separate from "couldn't search"

Task 5.5

Human-in-the-loop for automated pipelines

  • Route by field-level checks, not by an overall "looks good". Send a record to review when a required field is null, a cross-check fails, or a value is out of range.
  • Calibrate before trusting confidence. If you use model confidence for routing, first check it against a labelled set to see whether "0.9" really means 90% correct for this task.
  • Watch per-segment accuracy. A 97% overall rate can hide 70% on one document type. Measure by type, and use stratified sampling of auto-approved output so rare types still get human eyes.
  • Feed corrections back. Human fixes become new few-shot examples or eval cases.
Task 5.5

Human review, calibration and sampling

Before reducing human review, prove the automation is accurate where it matters.

Aggregate accuracy hides segments

Document typeShareField accuracy
Standard invoices82%99.1%
Credit notes11%96.4%
Handwritten receipts7%71.0%
Overall100%97.3%

Illustrative numbers. "97% overall" looks safe to automate; the handwritten segment clearly isn't. Check accuracy by document type and by field before cutting review.

Calibrating confidence

  1. Have the model output a confidence per field.
  2. Run on a labelled validation set and measure actual accuracy at each confidence level.
  3. Set the review threshold from that data (e.g. fields below 0.82 go to a human).
  4. Also route ambiguous or contradictory source documents to humans, prioritizing limited reviewer time.

Stratified random sampling

Even auto-approved, high-confidence extractions get a random sample checked, stratified by type so rare types are represented. This measures the ongoing error rate and catches new error patterns that confidence scores miss.

The confidence paradox

Raw self-reported confidence is a poor escalation trigger (Task 5.2). Field-level confidence calibrated against labelled data is a good way to route review (Task 5.5). The difference is the calibration step.

Task 5.6

Provenance and uncertainty in multi-source synthesis

Keeping "who said this, and when" attached to every claim through every step.

subagent outputclaim–source mapping
{ "findings": [
  { "claim": "Session-musician employment fell 12% between 2022 and 2025",
    "source": "https://example.org/labour-report-2025", "doc": "Labour Report 2025, p. 14",
    "excerpt": "…a 12 percent decline in session work…", "published": "2025-06-02",
    "method": "national survey, n=4,100" },
  { "claim": "Session-musician employment fell 4% between 2022 and 2025",
    "source": "https://example.com/union-survey", "doc": "Union member survey",
    "excerpt": "…down 4% among members…", "published": "2025-11-20",
    "method": "member survey, n=900" }
],
"conflicts": [{ "topic": "session employment change", "values": ["-12%", "-4%"],
                "note": "Different populations: national vs union members" }],
"gaps": ["No data found for film scoring"] }
  • Conflicting statistics: keep both with attribution and annotate the conflict. Let the coordinator decide how to reconcile. Don't pick one arbitrarily.
  • Dates: require publication or collection dates so that "2019: 30%" vs "2025: 45%" is read as change over time, not a contradiction.
  • Report structure: separate well-established findings from contested ones, and keep the sources' own characterizations and methods.
  • Formatting by content type: financial data as tables, news as prose, technical findings as structured lists. Don't force everything into one format.
  • Coverage annotations: say which areas are well supported and which have gaps because sources were unavailable.

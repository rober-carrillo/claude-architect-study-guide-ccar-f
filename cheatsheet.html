Harder parts and easy-to-miss facts

Points from the official task statements that the sections above don't cover, plus what candidates reported finding hard. Official means it is stated in the exam guide. Candidates means it comes from people who sat the exam or published prep material.

Orchestration details

  • Official The coordinator should choose which subagents to call based on the query, not run every query through the full pipeline.
  • Official Iterative refinement loop: the coordinator checks the synthesis for gaps, sends targeted follow-up queries to search and analysis, and runs synthesis again until coverage is enough.
  • Official Coordinator prompts to subagents should state the goal and quality criteria, not step-by-step procedures, so subagents can adapt.
  • Official Divide research scope by distinct subtopic or source type per subagent, so they don't duplicate each other.
  • Official Model-driven tool choice (Claude decides the next call) is a different thing from a pre-configured decision tree. Know which one a scenario describes.
  • Official Crash recovery: each agent writes its state to a known location, and on resume the coordinator loads a manifest and injects that state into the agents' prompts.
  • Official The Messages API is stateless, so every request must carry the complete conversation history.

Sessions

  • Official --resume <session-name> continues a named session. Use it when the earlier context is still mostly valid.
  • Official When resuming after code changed, tell the session which files changed so it re-analyzes only those, instead of exploring everything again.
  • Official If the earlier tool results are stale, a fresh session with an injected structured summary is more reliable than resuming.
  • Official fork_session creates independent branches from one shared analysis, for example to compare two testing strategies.
  • Candidates Context is full: use /compact. Exploring two alternatives: fork. Distractors swap these two.

Tools and MCP

  • Official System prompt wording can override good tool descriptions. A keyword-heavy instruction such as "always analyze the content" can steer Claude toward analyze_content. Review the system prompt as well as the descriptions.
  • Official Splitting tools and merging them can both be correct. Split a vague generic tool into purpose-specific ones (analyze_document → extract_data_points, summarize_content, verify_claim_against_source). Merging into one tool is "valid but more effort than a first step".
  • Official Replace generic tools with constrained ones, e.g. fetch_url → load_document that validates the URL.
  • Official 18 tools on one agent is too many. 4–5 per role, plus a few cross-role tools for frequent needs.
  • Official Forced tool_choice makes one step happen first (e.g. extract_metadata). Later steps then run in follow-up turns.
  • Official Use PostToolUse hooks to normalize mixed formats from different MCP tools (Unix timestamps vs ISO 8601, numeric status codes) before the model sees them.
  • Official Business-rule errors should carry retryable: false and a customer-friendly explanation the agent can pass on.
  • Candidates isError: true means the source couldn't be reached. isError: false with no results means it was reached and nothing matched. The coordinator should respond to each in opposite ways.

Claude Code configuration (the lowest-scoring domain for one candidate)

  • Official Skill frontmatter to know: context: fork (runs in an isolated subagent so verbose output stays out of the main session), allowed-tools (limits what the skill can do), argument-hint (prompts for a missing argument).
  • Official To change a team skill just for yourself, create a personal variant with a different name in ~/.claude/skills/ so teammates aren't affected.
  • Official Skills are loaded on demand, so they aren't reliable for conventions that must apply automatically by file path. Use .claude/rules/ globs for that, and CLAUDE.md for universal standards.
  • Official @import in a package's CLAUDE.md pulls in only the standards files relevant to that package.
  • Official Personal MCP servers live in ~/.claude.json. Shared ones go in .mcp.json.
  • Official The Explore subagent handles verbose discovery and returns a summary, so the main context isn't exhausted.
  • Official A common correct pattern is plan mode for investigation, then direct execution for the planned change.

Iterating with Claude

  • Official Interview pattern: in an unfamiliar domain, have Claude ask you questions first (cache invalidation, failure modes) before it implements anything.
  • Official Test-driven iteration: write the tests first (behaviour, edge cases, performance), then share the failures to guide each round.
  • Official Problems that interact go in one detailed message. Independent problems can be fixed one at a time.
  • Official When prose is read inconsistently, 2–3 concrete input/output examples work better than more prose.

Structured output and review

  • Official Put format normalization rules in the prompt alongside a strict schema, for messy source formatting (dates, units).
  • Official Few-shot examples also reduce hallucination in extraction, such as informal measurements, varied layouts, or required fields coming back empty.
  • Official A retry message should include the original document, the failed extraction and the specific error.
  • Official A detected_pattern field on review findings lets you analyze which patterns developers dismiss and find false-positive sources.
  • Official An independent review instance beats self-review and beats extended thinking in the same session.
  • Official "Run three passes and keep issues found twice" is a distractor. It hides real bugs that only show up some of the time.
  • Official A larger context window doesn't fix attention dilution. Splitting into passes does.

Batch arithmetic

Official If results are promised within 30 hours and a batch can take up to 24, you must submit at least every 4–6 hours. The worst case is a document that arrives just after a submission, waits for the next window, and then takes the full 24 hours. With 4-hour windows that is at most 4 + 24 = 28 h, leaving 2 h spare. Also, refine the prompt on a sample first so fewer documents need resubmitting.

The confidence paradox

Looks contradictory, isn't

The guide calls self-reported confidence unreliable as an escalation trigger, yet it also recommends field-level confidence scores for routing human review. The difference is calibration. A raw "confidence 8/10" used to decide escalation is wrong. Field-level scores whose thresholds were tuned against a labelled validation set, then used to prioritise reviewer time, are right. If an answer mentions calibration with labelled data, it's probably the good one.

Escalation fine print

  • Official Explicit request for a human: escalate right away, without investigating first.
  • Official Frustrated, but no request for a human, and the issue is easy: acknowledge it and offer to resolve it. Escalate only if they ask again.
  • Official The guide's policy-gap example is a customer asking to match a competitor's price when the policy only covers your own site's price changes. Escalate.

Synthesis and provenance

  • Official Require publication or collection dates so that numbers from different years aren't treated as contradictions.
  • Official Reports should separate well-established from contested findings.
  • Official Present each content type in its natural format: financial data as tables, news as prose, technical findings as lists. Don't force everything into one format.
  • Official To counter lost-in-the-middle, put a key-findings summary first and use explicit section headers.
  • Official If the downstream agent has a small context budget, change the upstream agent to return structured facts and citations instead of verbose reasoning.

Not on the exam

Official Fine-tuning, API authentication/OAuth and key rotation, billing, rate limits and pricing calculations, hosting MCP servers, streaming/SSE, computer use, vision, embeddings and vector DBs, cloud-provider setup, tokenization, and prompt-caching details beyond knowing it exists.

  • Candidates The real exam shares no questions with the practice test. Rising practice scores may only mean you've memorized those questions.

Night-before recall

One line each. If any of these surprise you, reread that section.

  • The loop continues on stop_reason == "tool_use" and ends on "end_turn".
  • Tool results go in a user message, matched by tool_use_id, all in one message per turn.
  • Subagents start with an empty context. Pass everything explicitly.
  • Parallel subagents come from several Task calls in a single turn.
  • Only a subagent's final message returns to the coordinator.
  • Critical business rules belong in hooks, not prompts.
  • PreToolUse can allow, deny, ask, or modify. Exit code 2 blocks a shell hook.
  • User ~/.claude/CLAUDE.md isn't shared. Project CLAUDE.md is.
  • .claude/settings.local.json is personal and git-ignored.
  • Skills: only name and description stay loaded until the skill is used.
  • .mcp.json = project scope. Secrets go through ${ENV}.
  • MCP tools appear as mcp__server__tool.
  • MCP tools are model-controlled, resources app-controlled, prompts user-controlled.
  • stdio servers must never write logs to stdout.
  • Tool errors: isError: true with category, retryability and next step.
  • Tool descriptions drive tool selection. Fix them first.
  • Schemas guarantee syntax, not semantics. Validate in code and retry with the error.
  • Nullable fields prevent fabrication.
  • tool_choice: auto, any, tool (forced), none.
  • Batch API: cheaper, async, up to 24h, no in-request tool loop, custom_id.
  • Keep a persistent facts block. Summaries lose numbers.
  • CI needs claude -p, or the job hangs waiting for input.
  • Review in an independent session, not the one that wrote the code.
  • Escalate on explicit request, policy gap, authority limit or no progress. Not on sentiment.
  • Ambiguous identity: ask for another identifier. Never guess.
  • Partial failure: continue and annotate coverage. Don't swallow, don't abort.
  • Check accuracy per segment, and sample with stratification.
